# AdVerse CRM — Production build

Что изменилось по сравнению с демо:

## Бэкенд (`/backend`) — новый, раньше не было
FastAPI + SQLite. Реализовано по ТЗ:

- **Проверка Telegram initData** по официальной HMAC-схеме (`backend/auth.py`) —
  каждый запрос к API проверяется, поддельный `initData` отклоняется.
- **Регистрация**: новый пользователь получает `role: "new"`, фронтенд
  принудительно показывает экран выбора роли, пока `/api/register` не
  вызван успешно.
- **Админка**: `ADMIN_IDS` в переменных окружения бэкенда → `is_admin: true`
  только для этих Telegram ID. CRUD агентов: `GET/POST /api/admin/agents/*`
  (список, создать, скрыть/показать, изменить % и реквизиты).
- **Изоляция данных**: заказы и пополнения хранятся с `owner_id` = проверенный
  Telegram ID из initData (никогда не берётся из тела запроса от клиента).
  `SELECT ... WHERE owner_id = ?` на уровне API.
- **Баланс**: начисляется на сервере в момент, когда агент/админ подтверждает
  пополнение (`/api/topups/{id}/status` → `confirmed`), а не на фронтенде.

## Фронтенд
- `js/api.js` — новый API-клиент, добавляет заголовок `X-Telegram-Init-Data`
  ко всем запросам.
- `js/data.js` — все захардкоженные массивы (`AGENTS`, `ORDERS`, `TOPUPS`)
  удалены, теперь заполняются из API после логина.
- `js/app.js` — логин теперь реально ходит на `/api/auth`, вход блокируется
  до прохождения регистрации; создание заказа/пополнения и админ-действия
  (скрыть/показать агента, изменить %, редактировать реквизиты) дергают
  реальные эндпоинты; при недоступном сервере показывается экран
  «Нет соединения», вместо пустого демо.
- Skeleton-заглушки при первой загрузке данных.

### Что осталось "как в демо" (сознательно, чтобы не раздувать объём)
`ACCOUNTS`, `TICKETS`, `NOTIFICATIONS`, `TEAM_MEMBERS` — по-прежнему локальный
мок в `data.js`. Они не завязаны на деньги/владельца заказа, поэтому в первую
итерацию бэкенда не попали. Если нужно — дописываются по той же схеме, что и
агенты/заказы (модель в `models.py`, эндпоинт в `main.py`, вызов в `api.js`).
Также: раздел агента (`agent-*` страницы) в демо был жёстко привязан к
"Agent #1" — я подключил реальные API-вызовы для принятия заказов и
подтверждения пополнений, но модель "какой Telegram-аккаунт = какой агент"
нужно будет доопределить под твою реальную схему (сейчас агент считается
привязанным к пользователю с ролью `agent`, но нет привязки конкретного
agent_id к конкретному Telegram ID — это стоит уточнить и добавить поле
`managed_agent_id` в `User`, если у каждого агента будет свой Telegram-логин).

## Как запустить

### 1. Бэкенд
```bash
cd backend
pip install -r requirements.txt
cp .env.example .env      # заполнить BOT_TOKEN, ADMIN_IDS, CORS_ORIGINS
python3 seed.py           # один раз — переносит 5 демо-агентов в БД как стартовый набор
export $(cat .env | xargs)
uvicorn main:app --host 0.0.0.0 --port 8000
```

Важно про хостинг бэкенда: **Vercel не подходит** для этого FastAPI+SQLite
сервера в режиме "как есть" — Vercel Functions бессостояние и не хранят файл
SQLite между вызовами. Варианты:
- Railway / Render / Fly.io / обычный VPS — держат процесс и файл БД постоянно.
- Если очень хочется на Vercel — нужно переезжать на внешнюю БД (Postgres,
  например Neon/Supabase) и разворачивать FastAPI как serverless-функцию.
Фронтенд (статика) прекрасно остаётся на Vercel — просто `apiBaseUrl` в
`js/config.js` должен смотреть на отдельно захостенный бэкенд.

### 2. Бот
```bash
cd backend
export BOT_TOKEN="..."
export MINI_APP_URL="https://your-frontend-domain.example.com"
export BOT_USERNAME="adverscrm_bot"
python3 bot.py
```
Напиши своему боту `/myid`, чтобы узнать свой Telegram ID и вписать его в
`ADMIN_IDS` на бэкенде.

### 3. Фронтенд
Открой `js/config.js`, пропиши `apiBaseUrl` на реальный адрес бэкенда, задеплой
папку как обычную статику (Vercel/Netlify/GitHub Pages), пропиши получившийся
URL в `MINI_APP_URL` бота и в BotFather (Menu Button / Web App URL).

## Проверка перед продакшном
- [ ] `DEV_BYPASS=false` на бэкенде (иначе подпись Telegram не проверяется)
- [ ] `BOT_TOKEN` бэкенда и бота совпадают (нужен один и тот же токен для HMAC)
- [ ] `CORS_ORIGINS` указывает на реальный домен фронтенда, не `*`
- [ ] `ADMIN_IDS` содержит именно твой Telegram ID
- [ ] SQLite-файл бэкенда лежит на постоянном диске (не эфемерном)

## Что добавлено во втором заходе (SaaS: доступ, подписка, рейтинги, тикеты, аудит)

### A. Управление доступом
- `User.is_approved` + `User.subscription_end_date` в `models.py`.
- `require_active_subscription()` в `main.py` — зависимость FastAPI, которая
  блокирует `POST /api/orders` и `POST /api/topups` для buyer/team, если
  подписка не активна, отдавая структурированную `403`:
  `{"detail": {"code": "SUBSCRIPTION_REQUIRED" | "SUBSCRIPTION_EXPIRED", "message": "..."}}`.
  Админы, агенты и саппорт этой проверке не подчиняются — это внутренние роли.
- Фронтенд (`api.js`) разбирает этот код и показывает модалку "Нужна подписка"
  вместо обычной ошибки (`showSubscriptionModal` в `app.js`).

### Б. Подписка (пока вручную, без платёжного шлюза)
- `GET /api/admin/users` — список пользователей с их ролью и статусом подписки.
- `POST /api/admin/users/extend {user_id, days}` — продлевает подписку и
  ставит `is_approved=true`. Доступно в приложении: Профиль/More →
  "Управление агентами" рядом теперь и раздел пользователей в админке
  (`page-admin-users`) с кнопкой "Продлить на 30 дней".
- Бот проверяет раз в 6 часов (`check_subscription_expirations` в `bot.py`,
  через `job_queue`) — кому подписка истекла и ещё не отправлено уведомление,
  и шлёт личное сообщение. Для `job_queue` нужен экстра-пакет
  `python-telegram-bot[job-queue]` (уже в `requirements.txt`).

### В. Рейтинг агентов
- Таблица `reviews` (`agent_id, user_id, rating 1..5, comment, screenshot_url`).
- `POST /api/agents/{id}/review` — оставить отзыв (создаётся любым
  зарегистрированным пользователем; ограничение "только если был заказ у
  этого агента" не реализовано — при желании легко добавить проверку по
  таблице `orders`).
- `GET /api/agents` теперь возвращает `avgRating`/`reviewCount`; звёзды в
  карточке агента (`formatStars`) используют реальный средний рейтинг.
- В деталях агента (`openAgentDetail`) — кнопка "⭐ Оставить отзыв".

### Г. Аудит-лог
- Таблица `audit_log` (`actor_telegram_id, actor_role, action, target, amount, meta, created_at`).
- Пишется при: создании/изменении/скрытии агента, продлении подписки,
  подтверждении пополнения (когда меняется баланс). Список — на странице
  "Логи" в админке (`GET /api/admin/audit-log`, до 200 последних записей).

### Д. Тикеты поддержки через бота
Поток именно такой, как просили: пользователь пишет в Mini App → бэкенд
пересылает это сообщение админу в личку через Telegram Bot API → админ
отвечает **реплаем** на это сообщение прямо в Telegram → бот (отдельный
процесс, `bot.py`) видит reply, сопоставляет его с нужным тикетом по
`message_id`, сохраняет ответ в БД и одновременно шлёт его пользователю
в личку. Ответ также появляется в Mini App при следующем открытии тикета
(`GET /api/support/tickets`).
- Таблицы `tickets` / `ticket_messages` в `models.py`.
- `POST /api/support/tickets`, `POST /api/support/tickets/{id}/messages`,
  `GET /api/support/tickets` в `main.py`.
- Пересылка админу — `telegram_notify.py` (прямой вызов Bot API, без
  зависимости от того, что `bot.py` вообще запущен, — сообщение дойдёт, даже
  если бот в этот момент перезапускается; а вот **ответ** админа поймает
  именно запущенный `bot.py`, так что держи его как постоянный процесс).
- Страница "Support" в приложении (`renderSupport`) переписана на реальные
  тикеты вместо мока.

### Е. Skeleton-заглушки
Все переписанные на API страницы (агенты, заказы через `showSkeleton()` при
входе, список агентов в админке, пользователи, аудит-лог, тикеты) показывают
`.skeleton-block` вместо пустого экрана, пока идёт запрос.

### Важно про миграцию БД
Если у тебя уже есть `adverse.db` от первого захода — в нём нет новых полей
(`is_approved`, `subscription_end_date`, `expiry_notified`) и новых таблиц.
`Base.metadata.create_all()` создаёт **только отсутствующие таблицы**, но не
добавляет колонки в уже существующие. Проще всего для старта — удалить
старый `adverse.db` и запустить `python3 seed.py` заново (агенты пересоздадутся
из демо-набора). Если в базе уже есть реальные заказы, которые жалко терять —
понадобится ручная миграция (`ALTER TABLE users ADD COLUMN ...`) вместо
удаления файла.

### Про сам BOT_TOKEN
Токен, который ты прислал в чат, теперь лежит в `backend/.env` — просто
для твоего удобства, чтобы сразу запускалось. Учитывай, что он побывал в
переписке: если это тебя беспокоит, в @BotFather можно перевыпустить токен
(`/token` → revoke) в любой момент — бот при этом не потеряет ни подписчиков,
ни настроек, только токен поменяется.

## v2.0 — Supabase (Postgres), строгие роли, is_paid, Центр управления

### 0. Переезд на Supabase
`backend/database.py` теперь смотрит на `DATABASE_URL` из `.env`. Если она
задана — подключается к Postgres (Supabase), если нет — падает обратно на
локальный SQLite (для разработки без интернета). Взять строку подключения:
Supabase → твой проект → Settings → Database → Connection string → URI.
Если хостинг бэкенда serverless — бери "Session pooler" URI, если обычный
постоянный процесс (Railway/Render/VPS) — можно direct connection.
Добавлена зависимость `psycopg2-binary` в `requirements.txt`.

**Важно про `db.commit()`**: я прошёл по всем местам, где меняются деньги/права
(`agent_update`, `agent_toggle`, `agent_create`, `admin_update_user`,
`extend_subscription`, `topup confirm`) — везде `db.commit()` вызывается сразу
после каждого изменения, до отправки ответа. Postgres здесь строже SQLite к
незакоммиченным транзакциям при параллельных запросах, но благодаря
`pool_pre_ping=True` в `database.py` мёртвые соединения (частая история с
Supabase pooler'ом после простоя) переоткрываются автоматически.

**Миграция схемы**: `Base.metadata.create_all()` создаёт только отсутствующие
таблицы, колонки в уже существующие не добавляет. Если это чистый новый
Supabase-проект — всё создастся правильно с первого раза (`is_paid`,
`managed_agent_id` и т.д. уже будут в схеме). Если ты уже гонял туда данные
по схеме v1 — либо снеси таблицы и дай `create_all` пересоздать их (`seed.py`
как и раньше накинет 5 демо-агентов), либо накати руками:
```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS is_paid boolean DEFAULT false;
ALTER TABLE users ADD COLUMN IF NOT EXISTS managed_agent_id integer REFERENCES agents(id);
```

### 1. Отображение ника — исправлено
Была реальная причина «криво отображается»: `js/app.js` в нескольких местах
(`renderProfile`, `renderMore`, `markAllRead`) брал статический объект-мок
`ROLES[state.role]` вместо реального профиля, собранного из ответа сервера.
Из-за этого в профиле всегда был фейковый `@alex_buyer`, даже когда бэкенд
уже отдавал правильный `username`. Поправлено:
- `_resolve_user()` в `main.py` при **каждом** входе сверяет `username` /
  `first_name` / `last_name` с тем, что прислал Telegram, и обновляет запись
  в БД, если ник поменялся — раньше это писалось только один раз при
  создании пользователя.
- `applyTelegramProfileToRole(role, apiUser)` теперь берёт имя и ник в
  первую очередь из ответа `/api/auth`/`/api/register` (то есть из БД), а не
  только из клиентского кэша `Telegram.WebApp`.
- `renderProfile`/`renderMore`/`markAllRead` переведены на `state.sessionRole`
  (живые данные) вместо `ROLES[state.role]` (статический мок).

### 2. Жёсткая иерархия ролей
- `_resolve_user()` в `main.py`: если `telegram_id` есть в `ADMIN_IDS` — роль
  `admin` и `is_admin=True` выставляются **принудительно на каждом входе**,
  независимо от того, что было в базе раньше. Если ID убрали из `ADMIN_IDS` —
  права снимаются на следующем же заходе.
  `VALID_ROLES` для самостоятельной регистрации сужен до `{"buyer", "agent"}` —
  Team и Support выдаются только админом через `/api/admin/users/update`,
  admin не выдаётся никогда и никак через `/api/register` (эндпоинт явно
  это проверяет).
- Фронтенд: `renderRolePicker()` рендерит только Buyer/Agent — Admin/Support
  физически не появляются в DOM экрана логина.
- Админ-панель (`page-admin-*`) как и раньше рендерится только при
  `state.isAdmin === true`, а реальный «щит» — это `require_admin()` на
  бэкенде, проверяющий `is_admin` на каждый `/api/admin/*` запрос.

### 3. `is_paid` и экран «Ожидание активации»
- `User.is_paid` (default `False`) в `models.py`.
- `require_paid_access()` в `main.py` (переименован из `require_active_subscription`
  прошлой версии) — блокирует `POST /api/orders` и `POST /api/topups`, если
  `is_paid=False`, отдавая `403 {"code": "PAYMENT_REQUIRED"}`.
- Страница «Тарифы» (`renderPricing`) для неоплаченных non-admin юзеров
  показывает экран «Ожидание активации» с кнопкой в Support, вместо списка
  планов.
- Админ (`is_admin=True`) не подчиняется этой проверке нигде — бесплатный
  доступ всегда, как и просили.

### 4. Центр управления (админка)
Страница «Пользователи» (`page-admin-users`) переписана:
- Поиск по `@нику` или `tg:ID` (клиентский фильтр по уже загрученному списку).
- Кнопка **в один клик** переключает `is_paid` (Активировать / ✓ Оплачено).
- Выпадающий список меняет роль (Buyer/Team/Agent/Support) —
  `POST /api/admin/users/update {user_id, role}`.
- Если роль = Agent, рядом появляется второй список — привязать этого
  человека к конкретному `Agent`-профилю (`managed_agent_id`), и кнопка
  быстрого перехода к его кошельку/%/лимитам (`openAdminAgentEdit`, уже
  существовавший CRUD агентов из первой версии).
- Другого админа редактировать нельзя — бэкенд отдаёт `400`, если пытаешься
  менять `is_paid`/роль/агента у пользователя с `is_admin=True`.

### 5. Уведомление о новой заявке
`_resolve_user()` при **создании** нового (не-админского) пользователя шлёт
всем ID из `ADMIN_IDS` сообщение через `telegram_notify.send_telegram_message`:
`🚨 Новая заявка: @username (ID: XXX). Ожидает подтверждения оплаты в админ-панели.`
— именно с текстом и форматом, как в ТЗ.

### Что не стал делать без уточнения
- Настоящий платёжный шлюз (сейчас `is_paid` переключается только вручную
  админом — как и было явно написано в ТЗ v2.0).
- Автоматическое согласование `is_paid` со старой `subscription_end_date`
  (поле оставлено в БД для совместимости, но никакой гейт на него больше не
  завязан — если хочешь вернуть автопродление/автоистечение подписки поверх
  `is_paid`, дай знать, это отдельная фича).
- Отдельная роль/экран для Team (мультипользовательская команда с общим
  дэшбордом) — она осталась как есть с первой версии, доступна только если
  админ вручную поставит роль `team` через новую админку.

## v2.1 — Разбор жалоб: персистентность, админка, роли, баланс/spend, интеграции

### 1. «Данные не хранятся»
Почти наверняка причина — на Render не задана переменная `DATABASE_URL`, и
бэкенд тихо падает обратно на локальный SQLite-файл, который живёт **внутри
контейнера Render** и стирается при каждом деплое/рестарте/засыпании free-тарифа.
Раньше это происходило молча. Теперь:
- При старте бэкенд явно печатает в логи Render, что использует:
  `✅ DB backend: Postgres (Supabase)` или `⚠️ DB backend: SQLite fallback!`.
- `GET /api/health` возвращает `db_backend`, `admin_ids_configured`,
  `bot_token_configured`, `cors_origins` — открой
  `https://<твой-render-домен>/api/health` в браузере и сразу увидишь, что
  реально подхватилось на проде.
**Чек-лист, чтобы данные начали сохраняться:**
1. Supabase → твой проект → Settings → Database → Connection string → URI
   (если бэкенд на Render — постоянный процесс, можно брать Direct connection,
   не обязательно Session pooler).
2. Render → твой Web Service → Environment → добавить `DATABASE_URL` с этой
   строкой (не забудь заменить пароль в URI на настоящий).
3. Redeploy. Проверить `/api/health` — должно быть `"db_backend": "postgres (Supabase)"`.
Дополнительно поправил `pool_pre_ping=True` в `database.py`, чтобы «уснувшие»
после простоя соединения с Supabase не роняли запросы, а переоткрывались.

### 2. «Админка коряво работает» + CORS
Убрал `allow_credentials=True` в CORS-настройке (`main.py`) — мы нигде не
используем cookies, только заголовок `X-Telegram-Init-Data`, так что эта
настройка была лишней и в отдельных браузерах могла давать себя знать. Также:
если `CORS_ORIGINS` не задан на Render — по умолчанию `*`, что в целом
рабочий, но небезопасный вариант для продакшна. Проверь, что на Render
выставлен `CORS_ORIGINS=https://<твой-домен>.vercel.app` (без слэша на конце,
можно несколько через запятую).
**Если админка всё ещё «не так» — пришли скриншот/текст ошибки из консоли
браузера (F12 → Console/Network) при открытии вкладки «Пользователи» —
конкретную причину я смогу увидеть сразу.**

### 3. «Не вижу новых юзеров, чтобы назначить роль» — баг найден и исправлен
Реальная причина: в `userRowHtml()` (app.js) выпадающий список ролей не
содержал варианта `role="new"` (это ещё не Buyer/Team/Agent/Support — юзер
только что открыл Mini App и ещё не нажал кнопку выбора роли). Браузер в
такой ситуации молча показывает **первый** пункт списка («Buyer»), поэтому
свежезарегистрированный пользователь визуально был неотличим от обычного
Buyer, и казалось, что его «нет» в списке. Теперь:
- Такие пользователи получают отдельный блок с бейджем «🆕 Новый» и двумя
  большими кнопками «Назначить Buyer» / «Назначить Agent».
- Список пользователей сортирует их наверх, а в подзаголовке страницы
  показывается счётчик «N новых».
- Админ может назначить роль и/или `is_paid` человеку даже **до** того, как
  тот сам пройдёт регистрацию в приложении — проверено тестом.

### 4. «Балансы зависшие, total spend должен быть 0»
Причина была прямая: страница «Мои аккаунты» и виджет Spend на дашборде
работали на захардкоженном моке `ACCOUNTS` в `data.js` — 5 фейковых
аккаунтов с зафиксированными цифрами ($420, $180, spend $120/$85...), которые
никогда не менялись, поэтому и выглядели «зависшими». Это полностью убрано.

### 5. «Нет интеграций, и их нельзя добавить»
Это тоже было правдой — раньше подключение Facebook API было кнопкой без
реального эндпоинта. Теперь это настоящая интеграция:
- Новая таблица `ad_accounts` (`models.py`) — реальный рекламный кабинет:
  ID кабинета + access token, привязанный к пользователю.
- `backend/facebook_api.py` — клиент Facebook Marketing API (Graph API v19):
  дергает `/act_{id}` (имя, статус, валюта), `/insights` с `date_preset`
  (today/last_7d/this_month/maximum) для spend, и `summary=total_count` для
  количества campaigns/adsets/ads.
- Эндпоинты: `POST /api/accounts` (добавить, вставив ID кабинета и токен),
  `POST /api/accounts/{id}/sync` (подтянуть свежие цифры), `DELETE /api/accounts/{id}`.
  Новый кабинет стартует с нулями и статусом `pending`, пока не синхронизирован.
  Если токен невалиден/нет прав — Facebook возвращает понятную ошибку,
  которая сохраняется как `last_error` и показывается прямо в интерфейсе,
  вместо того чтобы падать или показывать фейковые цифры.
- На фронтенде: страница «Мои аккаунты» — кнопка «+ Подключить рекламный
  кабинет» (вставляешь ID + токен), кнопка «Синхронизировать сейчас» на
  карточке, дашборд и «Аналитика» считают spend по-настоящему нулевым,
  пока ничего не подключено и не синхронизировано.

**Как получить токен для теста**: Facebook Business Manager → Business
Settings → System Users → создать/выбрать System User → Generate New Token
→ выбрать приложение и права `ads_read` (или `ads_management`, если нужно
больше) → токен привязать к нужному рекламному кабинету в правах доступа.
Это не требует App Review Facebook для базового `ads_read`, если аккаунт
уже принадлежит вашему Business Manager.
